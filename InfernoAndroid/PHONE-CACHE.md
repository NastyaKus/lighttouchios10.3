# 0.2.8: повтор патчей выбирал .InfernoOriginalBytes

На скриншоте после повторного запуска 0.2.7:

```
patching .../dyld_shared_cache_arm64e.InfernoOriginalBytes, 0 MB
mach_vm_map(size=21095563264, flags: 100) failed (error code=3)
Error: std::bad_alloc.
*** PATCHER: the patcher exited with 1
```

Это подтверждённая ошибка выбора входа. Прежний daemon перебирал readdir,
принимая любой файл с префиксом dyld_shared_cache, кроме содержащих .map.
После первой обработки FS patcher создаёт текстовый sidecar с исходными байтами;
при повторе он может оказаться первым в каталоге. Такой текст не является dyld
cache. Ошибка выделения ~19.65 GiB возникает при разборе неправильного файла;
сама по себе она не доказывает нехватку памяти для настоящего кэша.

Первый скриншот с `Changes applied successfully` / `*** PATCHER: --- end`
подтверждает вывод FS patcher, но не последующие umount System, mount Data,
запись отключённых служб и итоговый done. Причина первого зависания пока
не установлена: для неё нужен полный журнал, а не этот второй запуск.
`reloading after unclean unmount` означает, что APFS восстанавливает состояние
после нечистого отключения; это не подтверждение ни полной потери, ни целостности ФС.

## Изменение

- Новый GPL C daemon в guest/patcher-daemon.c использует только точный путь
  dyld_shared_cache_arm64e для поддерживаемой сборки 18A5351d. До запуска
  patcher проверяет magic dyld_v1, архитектуру arm64e и минимальный размер.
- Sidecar не удаляется и не переименовывается. Исходный FS patcher штатно
  использует его для отмены прежних изменений перед повторным применением.
- Перед/после mount/umount, перед записью служб — отдельные сообщения. Они
  позволят локализовать первый тип зависания. Таймаут целого шага остаётся час;
  отсутствие следующих строк не считается успехом.
- Запись override выполняется через временный файл, fsync и rename. Ошибки
  fork/waitpid, ненулевой/сигнальный выход дочернего процесса и umount не
  превращаются в успех. done появляется только после двух успешных umount.
- При patch-only запуске приложение каждый раз заменяет daemon в копии
  сохранённого ramdisk бинарником из текущего APK. Старые наборы обновляются
  без повторной подготовки, ASR, сброса дисков или изменения SEP state.
- Android QEMU/JNI .so, протокол USB и сам inferno_fs_patcher не менялись.

## Сборка без Mac

В guest/ находятся C-исходник, минимальные декларации публичного Darwin ABI,
TAPI link interface и build.sh. Apple SDK/библиотеки не распространяются.
LLVM clang + ld64.lld создают arm64 Mach-O с ad-hoc подписью, системную
libSystem загружает уже установленный гостевой ramdisk.

```sh
CLANG=/path/to/clang MACHO_LD=/path/to/ld64.lld guest/build.sh
python3 tools/guest-daemon-test/run.py
```

Поставляемый бинарник собран LLVM 17 из Swift Linux toolchain, без PAC:
SHA-256 f1b30d240bfbc31a5c636b369d10c687ca71523625241bb620e4a5725b601aa1.
При самостоятельной пересборке другим LLVM ожидаемо меняется SHA-256;
проверить результат и обновить pin в app/build.gradle.kts. Для обычной
сборки APK LLVM дополнительно не нужен: GPL бинарник включён рядом с исходником.

Проверено: 69 JVM-тестов, 8 host-тестов C daemon, lint без ошибок.
Реальный HFSX rewrite probe проверяет новый daemon побайтово; источник неизменен.
Production daemon стартовал в настоящем ramdisk на Linux QEMU/TCG (пустые
scratch-диски): новый marker, NAND ready, чистый выход QEMU, root sentinels прежние.

Отдельно тот же C-исходник в тестовом Mach-O выполнил **два полных синтетических
цикла внутри гостя**: fake device nodes/cache/mount/patcher, запись overrides и
umount. Получен first=0 second=0, QEMU exit 0, 11 с. Это проверка Darwin ABI,
fork/exec/wait, чтения/записи/rename/fsync и повторного выбора точного пути;
она не исполняла настоящий FS patcher и не монтировала APFS. Ни backup-first
Linux тест, ни этот прогон не доказывают корректность частично изменённого
пользователем dyld cache.

Ошибки подготовки дополнительного теста также зафиксированы: до remount -uw
scratch ramdisk не создавалась scratch-папка (put ENOENT); shell mocks возвращали
127, поэтому заменены копиями того же подписанного тестового Mach-O.
Изначальный runner завершал проверку при NAND ready, до окончания fake цикла;
добавлен флаг --expect-daemon-self-test, требующий оба результата 0.

Результаты и границы текущих проверок — validation-results.json.
На Linux нет записанного пользователем APFS root. Монтирование его томов,
завершение патчей, активация и первый запуск iOS остаются проверкой на телефоне.

## На телефоне

Установить APK **поверх** 0.2.7. Не удалять приложение, не готовить набор заново,
не выбирать полное повторное восстановление. Остановить предыдущую VM, затем
**Завершить патчи → Запустить патчи**. Ожидаемый вход содержит точное имя кэша
без .InfernoOriginalBytes и имеет размер около 1957 MiB.
Если остановится после обработки кэша — сохранить диагностику до следующего
запуска: новые строки показывают операцию, на которой остановился daemon.
