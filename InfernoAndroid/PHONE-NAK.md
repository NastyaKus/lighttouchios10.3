# 0.2.5: `USB OUT NAK 60s` во время ASR

## Наблюдения на телефоне

Диагностика 0.2.4 подтверждает успешные usbmux VERSION/setup, QueryType,
StartRestore и ответы на запросы RootTicket, NORData, FDRTrustData,
SystemImageData. Гостевой ASR дошёл до 68%; на экране отправителя осталось
2942/4916 МиБ. Завершение ASR, финальный StatusMsg, патчер и загрузка iOS
не подтверждены.

Новое логирование установило реальный device reserved word: **0xfaceface**.
Два поля заголовка различаются: например, первый SYN|ACK имеет seq12=0,
seq14=1; следующие ответы — (1,3), (2,5), (3,5). Offset 12 — номер устройства,
который хост возвращает в своём заголовке; offset 14 подтверждает номера хоста.
Это объясняет прежнюю несовместимость проверки 0xfeedface в приёмнике.

В текущей попытке гость сообщил `Expected 22384 received 22385/22386/22387`,
затем получил повтор диапазона, начинающегося раньше ожидаемого номера.
В журнале есть `reached max TRB block allocation for endpoint 0x81`, позже
`IO timeout ... endpoint 81`. Хост завершил отправку исключением
`SocketTimeoutException: USB OUT NAK 60s` из Asr.transfer → Channel.write.
Сервис остановил движок с кодом 0 и контролируемо завершил процесс VM.
Android сообщил lowMemory=false и около 5 ГБ доступной памяти: этот архив
не показывает прежний native crash или уничтожение процесса из-за RAM.

Частные журналы и исходный архив диагностики не входят в поставку.

## Подтверждённые проблемы планирования клиента

Swift-клиент имеет отдельный receive pump. В Kotlin один worker владеет
сокетом и состоянием протокола; до 0.2.5 чтение во время write происходило
прежде всего при заполненном TCP-окне или OUT NAK. Большое открытое окно
позволяло направлению IN долго оставаться без обслуживания.

Повтор отправлял последние 96 mux-пакетов без учёта cumulative mux ACK,
включая уже принятые пакеты, и без чтения IN после каждого успешного OUT.
Отброшенные дубликаты провоцируют ответы; такой burst усиливает давление
на гостевую очередь endpoint 0x81. Повтор не является признаком потери сам
по себе: при подготовке NOR или занятом госте мог закончиться таймер тишины.

По журналу нельзя доказать первопричину самого первого потерянного кадра
внутри DWC3. Исправление устраняет выявленные проблемы клиента, но не
объявляет весь контроллер или восстановление проверенными.

## Изменения

- Cumulative ACK из offset 14 удаляет принятый префикс из истории повтора.
  Префикс удаляется только при совпадении с сохранённым номером; старое
  подтверждение не должно удалить новые кадры после переполнения счётчика.
- Повтор содержит только оставшиеся неподтверждённые кадры и читает IN после
  каждой отправки. Содержимое пока буферизуется: новый TCP ACK не должен
  обогнать старые mux-номера, которые ещё повторяются.
- Channel.write обслуживает IN между пакетами даже при свободном TCP-окне.
  Если уже накопились ответы от повтора, перед их разбором читается и сам
  endpoint: наличие данных в локальном буфере не означает пустую очередь USB.
- Перед решением о повторе сначала обслуживается входящий пакет. Полностью
  подтверждённая история не повторяется из-за одной лишь тишины гостя.
- Старый TCP ACK не сдвигает счётчик подтверждённых байтов назад и не меняет
  окно. Подтверждение ещё не отправленных байтов по-прежнему отвергается.
- При долгом OUT NAK в журнал добавляются время, длина, mux sequence,
  последний peer ACK, размер истории и число прочитанных байтов. Payload,
  тикеты и ключи не логируются. Предел OUT NAK остаётся **60 секунд**.
- Изменены Kotlin-код и версия APK; native engine/JNI не меняются.

## Проверки без Apple-файлов

```sh
./gradlew :app:testDebugUnitTest :app:assembleDebug :app:lintDebug
```

Модель USB проверяет wire headers и порядок mux хоста; она может потерять
кадр после успешного USB OUT и отвергает следующие номера до его повтора.
Абстрактная очередь IN ограничивается **двумя** записями. Это стресс-модель,
не измеренное значение TRB лимита Apple и не исполнение DWC3.

Новые регрессии проверяют:

- чтение IN при большом свободном окне;
- потерю кадра, выборочный повтор и отсутствие повторов принятого префикса;
- занятого гостя с mux ACK без TCP ACK;
- OUT NAK с одновременными входящими данными без нарушения mux-порядка;
- устаревшие TCP ACK и отказ на ACK неотправленных байтов;
- 65 540 отправок по 256 байт с потерей номера 65535 и восстановлением
  обмена через переполнение 16-битного счётчика;
- отказ по 60-секундному OUT NAK и наличие диагностических полей.

В первом прогоне новой реализации стресс-тест потери кадра обнаружил
`Fake guest IN endpoint queue overflow`: разбор локального backlog продолжал
мешать чтению самого endpoint. После добавления чтения при непустом локальном
буфере тест повторяется с тем же малым пределом очереди. Финальные результаты
сборки и тестов находятся в validation-results.json.

Финальный прогон: **55 JVM-тестов прошли**, lint — 0 ошибок / 23 предупреждения,
APK versionCode 7 подписан прежним сертификатом и проходит zipalign 16 KiB.
Все native .so побайтово совпали с APK 0.2.4.

Дополнительно выполнено сравнение с кодом 0.2.4, commit 0aaa1f4. Три тех же
новых теста воспроизвели две ошибки `Fake guest IN endpoint queue overflow`
и повтор уже принятого отправления у занятого гостя. Для запуска старого кода
добавлен только адаптер clock/constructor, политика обслуживания не изменялась.
Счётчик fake-модели в busy-guest сценарии вырос с ожидаемых 256 до 1024 байт;
это свидетельство лишних отправлений в модели, а не утверждение о повторной
записи этих байтов реальным ASR на диск.

```sh
JAVA_HOME=/path/to/jdk GRADLE_USER_HOME=/path/to/gradle-cache \
  python3 tools/usb-replay-regression/run.py
```

Требуются собранные актуальные JVM tests и cached Kotlin/JUnit. Без истории git
можно задать EMBER_BASELINE_GUEST_USB — путь к исходному GuestUsb.kt версии
0.2.4 из validation в архиве обновления. Результат сравнения —
build/usb-replay-regression/baseline-results.json.

## Повтор на Android

Установить 0.2.5 поверх имеющегося Ember VM. Сохранённые IPSW и подготовленные
компоненты подходят для повтора; нажать «Повторить восстановление» и подтвердить
очистку дисков незавершённой попытки. Новая подготовка или переустановка с
удалением данных не требуется. При новом сбое сохранить диагностику до
следующего повтора. Полный restore и первый boot 0.2.5 остаются непроверенными.
