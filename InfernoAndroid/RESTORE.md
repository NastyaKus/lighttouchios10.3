# Ember VM: экспериментальный установщик iOS 14 на Android

Продолжение InfernoAndroid из ветки `ccr-38a9e977-ffrrse`, база
`d453a1b4563dffd8d90f9a43b86ab45b15580e8d`. Новый application ID —
`dev.embervm.android`, имя — **Ember VM**. Старое приложение и его данные
автоматически не переносятся. Исходная версия QEMU сохранена; Android-правки перечислены в `engine/patches/`.
Начиная с 0.2.3 добавлена узкая правка переключения контекста ARM64 (описание ниже).
Архив iPhone 5 не участвует в сборке и не меняется.

## Что можно сделать с телефона

1. Установить arm64 APK на Android 10 или новее. Остановить запущенную VM и импорт.
2. Открыть «Восстановить из IPSW». Нужны не менее **15 ГиБ свободного места**,
   зарядка и достаточно RAM для гостя (по умолчанию 3 ГиБ) вместе с Android и TCG.
   На Android тоже есть LMK и ограничения производителя: отсутствие iOS jetsam
   не гарантирует, что процесс переживёт восстановление.
3. Выбрать локальные файлы:

   | Вход | Требование / источник |
   |---|---|
   | IPSW | `iPhone11,8,iPhone12,1_14.0_18A5351d_Restore.ipsw`, оригинал с CDN Apple; строго 18A5351d, n104ap Erase |
   | ticket.shsh2 | XML plist с `ApImg4Ticket`, [ChefKiss File Setup](https://chefkiss.dev/guides/inferno/file-setup/) |
   | SEP ROM | `AppleSEPROM-Cebu-B1`, согласно тому же руководству; правильность ROM ещё должен подтвердить гость |
   | SEP IV + key | 96 hex: 16 байт IV + 32 байта AES key; [The Apple Wiki](https://theapplewiki.com/wiki/Keys:AzulSeed_18A5351d_(iPhone12,1)) для этой сборки |

   Установщик не скачивает файлы Apple и не обращается к TSS. Ключ не пишется
   в настройки/журнал; при подготовке он живёт в памяти процесса.
4. Нажать «Подготовить набор». Приложение копирует IPSW в собственную папку,
   проверяет каталог ZIP/ZIP64, распаковывает компоненты с CRC, преобразует тикеты,
   расшифровывает SEP AES-256-CBC/NoPadding и собирает IMG4 `rsep/none`.
   Успешный AES-CBC **не проверяет правильность ключа**: аутентификации у CBC нет.
5. Нажать «Начать восстановление». Сервис `:vm` запускает исходный ramdisk, ждёт USB,
   выполняет QueryType/StartRestore и запросы restored, передаёт OS прямо из
   несжатого ZIP-member через ASR. Можно открыть экран гостя и консоль.
6. После `StatusMsg=0` с ответом `ReceivedFinalStatusMsg` VM остановится,
   сохранив записанные диски. Нажать **«Завершить патчи» → «Запустить патчи»**.
   Это отдельный запуск ramdisk с отключённым восстановителем, без повторного
   ASR и без очистки дисков. Такой порядок введён в 0.2.6 после наблюдавшегося
   `Halt/Restart Timed Out`: аппаратный hold-reset не отменяет shutdown гостя.
   С 0.2.7 отдельный job выполняет штатный nvmefwupdater --skip, чтобы открыть
   сохранённые разделы; USB-подключение восстановителя на этом этапе не требуется.
   С 0.2.8 daemon обновляется и в ранее подготовленном наборе: выбирается
   точный dyld_shared_cache_arm64e, а не его .InfernoOriginalBytes sidecar.
   Подробности повторного запуска и ограничения — [PHONE-CACHE.md](PHONE-CACHE.md).
   С 0.2.9 отключение томов использует Darwin unmount(path, 0):
   в ramdisk нет /sbin/umount. См. [PHONE-UNMOUNT.md](PHONE-UNMOUNT.md).
   С 0.3.0 повтор сначала проверяет все 45 целевых изменений; полностью
   совпадающий кэш не переписывается. Ненулевой child exit ждёт завершения
   cleanup, а успех требует readback карты. См. [PHONE-REPEAT.md](PHONE-REPEAT.md).
   С 0.3.1 пять служб отключаются в binary cache launchd на System с
   резервной копией и readback. Монтирование Data на стадии патчей не требуется.
   Это не доказывает его доступность при обычной загрузке. См. [PHONE-DATA.md](PHONE-DATA.md).
7. Завершение требует выхода патчера с кодом 0, подтверждения записи отключённых служб и `done`, затем
   остановки QEMU с кодом 0. Только после этого набор становится активным.
   Первый запуск iOS / SpringBoard остаётся отдельной проверкой.

Подготовка идёт в `files/restore-staging/`, текущий `InfernoData` сохраняется.
Девять новых файлов создаются разреженными: root 32 ГиБ, firmware 8 МиБ,
syscfg 128 КиБ, ctrl_bits/nvram по 8 КиБ, effaceable 4 КиБ, panic_log 1 МиБ,
sep_nvram 64 КиБ, sep_ssc 128 КиБ. Seed от реального устройства не используется.

После успешной остановки машины старые `InfernoData` и ROM перемещаются в
`restore-backup-<timestamp>/`, новые — на их место. Локальная рабочая копия IPSW
удаляется только после активации; выбранный исходный файл не удаляется.
Проверяйте предыдущий набор перед удалением резервной копии.

Отмена останавливает VM и оставляет неактивную попытку. После прерывания процесса
можно повторить полный restore с очисткой дисков. Если успешная запись системы
подтверждена квитанцией или текущими журналами 0.2.5, доступен отдельный повтор
патчей, сохраняющий диски. Если прервалась активация, журнал
`restore-activation.plist` блокирует новую подготовку/обычный запуск; кнопка
«Вернуть предыдущий набор» возвращает резервные файлы и сохраняет новый диск
в `restore-backup-*/unactivated/`. Это защита от прерывания процесса, а не
гарантия атомарности двух каталогов при потере питания/повреждении накопителя.

## Что изменяется в загрузочной цепочке

- AP/SEP ticket **пересобираются**, а не подписываются Apple. Digests берутся из
  build identity; SEP получает ECID/nonce эмулятора и изменённую копию манифеста
  в сертификате. Такие тикеты предназначены для патченной реализации Inferno,
  не для восстановления физического iPhone.
- Используется существующий патченный t8030/SEP движок. Порт не заменяет ROM,
  не добавляет новый exploit физического устройства и не меняет QEMU.
- `RestoreRamdisk` заменяет два имеющихся NFC-файла на `inferno_patcher` и
  `inferno_fs_patcher`, а disabled syslogd job — на launchd job демона.
  Редактируются HFSX forks, bitmap, размер, режим и compressed flag.
  Для отдельного patch-only запуска отключается launchd job восстановителя
  в копии ramdisk; установленная iOS этим изменением не затрагивается.
  Нет вставки записей в B-tree; overflow extents и повреждённые структуры
  отклоняются. Модифицированный ramdisk нужен для применения патчей ФС гостем.
- Guest daemon правит dyld shared cache и отключает пять служб. Полноценный
  jailbreak bootstrap (apt/dpkg, пакеты и т. п.) этим портом не устанавливается.

В APK входят только открытые программы гостя из Inferno-iOS v0.3.1. Gradle
проверяет SHA-256 IPA
`c66b56de80d55b989df1c70ebcf4b321751a6703a9d253c9ff349f434fd7c8dc`
и извлекает ровно два файла, не Apple payload. Недоступная загрузка позволяет
собрать APK без программ; такой restore имеет результат `INCOMPLETE /
RESTORED_NEEDS_PATCHES`, набор не активируется. Неверный SHA останавливает сборку.

Лицензия исходников эмулятора не предоставляет лицензию на iOS или SEP ROM.
Получение и использование файлов Apple регулируются их условиями, которые
могут ограничивать виртуализацию на Android. Техническая реализация не
подтверждает право распространения готового образа; образ iOS здесь не включён.

## Проверка разработчиком на Linux

```sh
# SDK/NDK и сборка неизменённого движка — как в README.md.
cd InfernoAndroid
python3 tools/generate_restore_fixtures.py
./gradlew :app:testDebugUnitTest :app:assembleDebug :app:lintDebug
# Требуется отдельный checkout Swift-оригинала на точном коммите:
tools/swift-parity/run.sh /path/to/Inferno-iOS /path/to/swiftc
```

База порта: [MakrSas/Inferno-iOS @ 4bc3970](https://github.com/MakrSas/Inferno-iOS/tree/4bc39702871f5a118d96acbad4df7a675ddf14e0).
Синтетические fixtures создаёт Python независимо от Kotlin. Ни fixture
`ticket.shsh2`, ни HFSX-volume не являются файлами Apple или готовой системой.
Swift harness компилирует неизменённые IMG4.swift, Ticket.swift,
RestoreRamdisk.swift; Linux добавляет только L()/autoreleasepool scaffolding.

Проверяются DER (long tags, unsigned integers, границы/вложенность), AP/SEP
certificate rewrite, IMG4, AES-256-CBC NIST SP 800-38A, XML data/типы/ошибки,
stored/deflate/ZIP64/CRC/path traversal, HFSX allocation и отказ без публикации,
аргументы обычного/restore запуска, финальный restored status, NOR iBoot-first,
FUD/preflights, FileData 8192, fragmented/coalesced unframed ASR, OOB bounds,
SHA-1 по 131072 байта, CRC OS, USB enumeration, VERSION/setup, SYN/ACK,
scaled TCP window, MTU 16 КиБ, ASYNC, short OUT, неверный ID и sequence gap.

USB тест использует независимый эмулятор байтового протокола через `UsbLink`.
Он **не исполняет Android JNI/socketpair**, не доказывает производительность
реального контроллера и не заменяет физический Android-тест.

## Состояние проверки на Android

1. Установка/открытие APK, SAF-права, уведомления, отмена и возобновление после LMK
   на конкретном телефоне. В стенде нет подключённых Android-устройств.
2. Нативный Unix listener/accept/ParcelFileDescriptor под SELinux, реальная USB
   enumeration и поток ASYNC/NAK. Проверка ELF/JNI-символов статическая.
3. В диагностике 0.2.5 с телефона подтверждены загрузка restore ramdisk/SEP,
   QueryType, передача системы/прошивок и успешный финальный статус restored.
   Это один конкретный телефон/набор. Новый двухэтапный запуск 0.2.6,
   отключённый restore monitor и миграцию сохранённых дисков нужно проверить.
   Неизвестный запрос явно завершает попытку ошибкой. Поддерживается только iOS 14.
4. Успех гостевого патчера, корректная остановка, запуск активированного raw-диска,
   SpringBoard и постоянство данных после следующей загрузки.
5. Ошибки прошивки/патчера, заполненный диск, длительная работа в фоне, перегрев
   и давление RAM. Возможен принудительный kill VM через 15 секунд остановки.

Результаты и конкретные ошибки этой сборки записаны в [VALIDATION.md](VALIDATION.md).
Журналы на телефоне: `files/restore-status.plist`, `files/restore.log`,
`files/restore-staging/guest-console.log`, `files/restore-staging/logs/engine.log`.
Статус PREPARED и наличие 15 файлов не означают успешную загрузку iOS.

Если запись уже завершилась на 0.2.5, а на патчах произошла паника,
обновить приложение и выбрать **«Завершить патчи»**, сохранив данные приложения.
Подробности и ограничения — [PHONE-REBOOT.md](PHONE-REBOOT.md).
Если 0.2.6 остановилась на waiting for the restore to finish, причина и правка
описаны в [PHONE-NVME.md](PHONE-NVME.md): обновить APK и повторить только патчи.

## Обновление 0.2.1: сбой и повтор на телефоне

Сообщение старой 0.2.0 «Предыдущая попытка прервана» вызывается оставшимся
файлом `restore-running`. Оно не сообщает причину первоначального исчезновения
процесса. Консоль при этом могла относиться к предыдущему запуску.

В 0.2.1 активная попытка защищена OS file lock в private filesDir; Android
освобождает её при завершении процесса. Оставшийся информационный marker больше
не блокирует повтор. Повтор после подтверждения очищает только рабочие диски
незавершённого восстановления, используя уже скопированный IPSW и подготовленные
компоненты. Активный набор не меняется. Хвосты старых журналов сохраняются до
очистки рабочих дисков. Дополнительные 5.5 ГБ повторно копировать не нужно.

Устанавливайте 0.2.1 поверх 0.2.0 без удаления приложения и очистки данных.
Перед повтором нажмите **«Сохранить диагностику»**, сохраните ZIP через системное
окно Android и приложите файл к сообщению. В него входят последние журналы,
исключение Java при его наличии, настройки памяти и сведения Android о причинах
завершения процессов (Android 11+). Нативный crash, LMK и контролируемая остановка
не объявляются одной и той же причиной. В архив не добавляются IPSW, диски,
ROM, тикеты или введённый SEP key. Восстановление на устройстве по-прежнему
не считается проверенным до фактического завершения и первого запуска.

Исправлена ссылка на ключи: верная страница — **AzulSeed 18A5351d**, не Sky.


## 0.2.3: локализованный SIGILL в контексте корутин

Новый native tombstone показал `SIGILL / ILL_ILLOPN` на `autiasp` в Android
`libc longjmp`, вызванном из `qemu_coroutine_switch` при первом USB SETUP.
Это уже конкретная функция и инструкция, а не вывод по последней строке
гостевой консоли. Проверка PAC на адресе возврата завершается ошибкой при
использовании bionic siglongjmp как механизма переключения стека QEMU.

Вместо замены движка добавлен Android/AArch64-only patch
`0003-android-aarch64-coroutine-context.patch`. Он адаптирует контекст из
AlexZorzi/Inferno-Android @ 228965f4746eb022592615c4fc9a69f4896ead61,
с отдельными скрытыми символами, returns_twice/noreturn и сохранением Android
thread-local x18. Системный longjmp и глобальная политика PAC не меняются.

Проверка без Apple-файлов:

```sh
ANDROID_NDK_HOME=/path/to/ndk QEMU_AARCH64=/path/to/qemu-system-aarch64 \
  tools/native-coroutine-test/run.sh
```

Freestanding ARM64 ELF проверяет x19–x30/SP, d8–d15, сохранение текущего x18,
значение 0→1 и 100000 переключений на отдельный стек с проверкой локальных
данных. Прогоны cortex-a57 и max с доступным PAC проходят. Это проверка
примитива на ARM64 TCG; полный Android restore нужно проверить на телефоне.

Установить обновление поверх прежней версии и выполнить «Повторить
восстановление» из уже подготовленного набора. При новом сбое сохранить ZIP
диагностики: он содержит текущий native tombstone и первые USB команды.

## 0.2.4: `Mux magic` после согласования USB

Последний телефонный лог 0.2.3 показывает USB/usbmux v2 без прежнего SIGILL,
затем отказ Kotlin-приёмника `Mux magic`. В 0.2.4 приём заголовков приведён
к исходному Swift: входящее поле не обязано совпадать с host magic,
mux-счётчик не используется для фильтрации TCP-пакетов. Добавлены тесты и
отдельный ограниченный trace заголовков без содержимого. Подробный разбор —
[PHONE-MUX.md](PHONE-MUX.md).

Обновить APK поверх прежнего приложения. Набор и скачанные файлы сохраняются;
использовать повтор восстановления, подтвердив очистку его целевого диска.
При следующей ошибке сохранить новый ZIP диагностики. Прохождение mux
само по себе не подтверждает восстановление или загрузку iOS.

## 0.2.5: остановка ASR с `USB OUT NAK 60s`

0.2.4 на телефоне дошла до ASR, но после потери порядка mux-пакетов появились
переполнение очереди ответов USB и таймаут. В 0.2.5 читается IN между исходящими
пакетами, в том числе во время повтора; уже подтверждённые mux-пакеты не
повторяются. Длинный OUT NAK оставляет подробный журнал заголовков и ожидания.
Таймаут не увеличен. Обоснование и тесты — [PHONE-NAK.md](PHONE-NAK.md).

Установить обновление поверх прежнего приложения и нажать «Повторить
восстановление». Сохранённый набор не нужно готовить заново. Рабочие диски
попытки очищаются после подтверждения, затем ASR начинается сначала; продолжение
передачи с 2942 МиБ не реализовано. Испытание на настоящем госте ещё необходимо.
