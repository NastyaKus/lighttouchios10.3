# 0.3.0: проверка уже применённых патчей и ожидание cleanup

Диагностика телефона 0.2.9:

- выбран правильный 1957 MiB dyld_shared_cache_arm64e;
- перед Building patches нет подтверждения Reverted;
- no blra instruction found start_addr=6577993120 (0x1881435a0), child exit 1;
- начат настоящий APFS unmount System, но нет строки о его результате;
- хост уже записал FAILED и остановил QEMU.

Архив предыдущей успешной попытки 0.2.8 содержит Reverted, exit 0, Changes
applied successfully и 45 четырёхбайтовых замен. Область ошибки соответствует
ранее изменявшемуся QuartzCore dispatch коду. Отсутствие Reverted может означать
отсутствующий/пустой sidecar; его фактических байтов в диагностике нет.
Повреждение остального кэша этим журналом не исключается и не подтверждается.

## Исправление порядка остановки

В 0.2.9 host loop немедленно выбрасывал исключение при ненулевом exitCode
дочернего FS patcher. Daemon в этот момент только начинал unmount. Это ошибка
обвязки: чистый выход host QEMU не доказывает flush metadata внутри гостя.

0.3.0 ждёт cleanup complete перед обработкой child failure. Daemon выполняет
sync перед unmount, fsync кэша и имеющегося sidecar после успешных патчей;
cleanup marker появляется после отключения разделов/завершения очистки.
Запись служб тоже отключает Data при ошибке записи. Ошибки unmount остаются
ошибками, принудительное отключение не добавлено. Паника гостя/общий часовой
таймаут по-прежнему прерывают попытку; безопасный flush при kernel panic
гарантировать нельзя.

## Повтор без записи уже готовых изменений

В guest/plans/18A5351d-v031-software.json включена точная карта 45 замен
(180 генерируемых патчером байтов), полученная из успешного вывода того же
pinned FS patcher на строго поддерживаемой 18A5351d/n104ap. Исходные Apple
инструкции, пользовательский cache, ROM/ticket или сырые логи не включены.
C header воспроизводимо генерируется plans/generate.py.

Daemon перед запуском C++ читает все 45 участков по смещениям. Только если
совпали ВСЕ байты, кэш не переписывается и патчер не вызывается повторно.
Это проверка целевой карты изменений, **не контроль целостности всего 2-GB
кэша**. Имя/magic/arm64e/границы проверяются отдельно; разрешена только та же
сборка из подготовленного набора.

Если карта неполна, запускается прежний штатный patcher. Его exit 0 теперь
также требует полного readback 45 участков перед продолжением. Ошибка поиска,
любой несовпавший участок после patcher exit 0, fsync или unmount не считаются
успехом. Пропуска отдельных патчей и безусловного игнорирования code 1 нет.
В зависимости от наличия sidecar штатный patcher может откатить свои прежние
изменения перед повтором; его действия не объявляются read-only.

Новая явная строка успеха карты:

```
*** PATCHER: patch plan verified 18A5351d-v031-software all=45
```

Для завершения также нужны отключённые службы, cleanup complete, done и чистый
выход QEMU. При reuse не печатается фиктивный child exit 0. Старые done/exit 0
без readback/cleanup больше не подходят. Android UI отражает ожидание flush.

## Проверки и ограничения

- 72 JVM tests, в том числе child exit 1 до/после cleanup, неверный plan ID/count,
  reuse без child exit и запрет успеха по exit 0 + done без проверки карты.
- 13 C host tests: реальная production карта на sparse 1957 MiB файле, повтор
  без sidecar/без запуска patcher, несовпадение 1 из 45, усечённый файл,
  отказ unmount, ошибка записи overrides и порядок cleanup.
- C host tests перехватывают umount2 и sync: mountpoints хоста не отключаются.
- Guest synthetic probe использует ДРУГУЮ маленькую карту из двух участков,
  fake APFS/cache/patcher, настоящий tmpfs unmount на /mnt9 и реальные POSIX
  read/fsync/sync/rename. Маленькая карта не может быть принята Android host,
  где разрешены только production ID/count 45. В APK только production daemon.
- Первый Linux guest probe упал с kernel data abort до запуска launchd/daemon,
  как уже бывало на этом стенде. Успех последующего прогона/конкретные значения —
  validation-results.json. Причина ранней panic не установлена.

Байты фактического кэша пользователя на Linux недоступны. Совпадение его 45
участков, продолжение Data mount/unlock, запись служб, APFS unmount/активация и
первый iOS boot проверяются на телефоне. При несовпадении новая диагностика
содержит matched/total; готовность iOS не утверждается заранее.

Установить APK поверх 0.2.9 и выбрать **Завершить патчи → Запустить патчи**.
Повторный erase/подготовка не нужны для этой проверки. Если проверка не пройдёт,
сохранить диагностику до следующего повтора; текущий набор не удалять.
