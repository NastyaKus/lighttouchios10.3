# 0.2.6: `Halt/Restart Timed Out` после успешного restored

## Что произошло в 0.2.5 на телефоне

Запись системы и прошивок завершена: host получил StatusMsg 0, отправил
ReceivedFinalStatusMsg и записал `restored: Status 0 подтверждён`. Гость
сообщил FINISHED-ENGINES:(SUCCESS), `restore-outcome = success`, затем
FINAL-MONITOR:(SUCCESS). Ошибка OUT NAK из 0.2.4 не оборвала эту попытку.

Патчер успел смонтировать System и начать обработку
dyld_shared_cache_arm64e размером 1957 МиБ. Время по консоли гостя:

| Событие | Время UTC |
|---|---|
| mount_apfs успешен, patching cache | 17:52:19 |
| финальный монитор восстановителя просит reboot | 17:52:21 |
| `/sbin/reboot`, launchd начинает shutdown | 17:52:24 |
| далее | kernel panic: **Halt/Restart Timed Out** |

Ни выхода патчера, ни five-services marker, ни done нет. Состояние CANCELLED /
InterruptedException в конце Android-журнала относится к последующей ручной
остановке ожидания, а не к первоначальной причине паники.

## Почему hold-reset недостаточно

Свойство SMC подавляет аппаратный reset и действие watchdog в эмуляторе.
Оно не отменяет `/sbin/reboot`, shutdown launchd, завершение процессов и halt
ядра. В исходном Swift/guest-daemon предполагалось, что оставшегося окна хватит
патчеру; комментарий самого демона предупреждает о последующей панике.
На этом телефоне патчер не успел завершить обработку большого кэша до shutdown.

## Два отдельных запуска

1. **Запись iOS:** исходный stock RestoreRamDisk из рабочей копии IPSW,
   без запущенного daemon-патчера. Прежние QueryType/StartRestore/ASR/прошивки.
   После Status 0/ACK хост останавливает QEMU с кодом 0, сохраняет отдельную
   квитанцию `restore-staging/restored.plist`. Результат — INCOMPLETE /
   «iOS записана, завершите патчи», без активации гостевого набора.
2. **Патчи:** новый процесс :vm; все девять дисков и SEP state сохраняются.
   Из уже внедрённого ramdisk создаётся отдельный `patch-ramdisk.im4p`:
   существующая launchd-запись com.apple.restored_external заменяется XML job
   с Disabled=true, RunAtLoad=false, KeepAlive=false. Исходный injected ramdisk
   сохраняется. Никаких изменений установленного `/sbin/reboot` или ядра нет.
3. USB listener остаётся необходим движку, но patch-only режим **не выполняет
   enumeration, QueryType или StartRestore**. Работает прежний patcher-daemon.
   Поэтому восстановитель не начинает новый erase и не вызывает reboot в конце.
   Уточнение 0.2.7: accept USB тоже не ожидается, а отдельный job запускает
   nvmefwupdater --skip для завершения NAND handshake; см. PHONE-NVME.md.
4. Успех требует exit 0, five-services и done. Затем — чистая остановка QEMU,
   прежняя активация с резервной копией. Первый boot iOS — отдельная проверка.

Режим патчей не выполняет setLength/truncate дисков, не пересоздаёт SEP/NVRAM,
не перепаковывает тикеты и не просит SEP key. Native engine и JNI неизменны.
При `panic(cpu ...)` ожидание патчера заканчивается ошибкой вместо часа ожидания.

## Сохранённая попытка пользователя из 0.2.5

До этой версии квитанции не было. Для перехода используются только текущая
консоль гостя и последний USB-сеанс host.log: Status 0 должен быть после
последнего USB RESET; гостевые FINISHED-ENGINES и FINAL-MONITOR должны сообщать
SUCCESS, а restore-outcome — success. Проверяются build, GuestTools, размеры
всех девяти дисков и непустой начальный участок root. Это базовая проверка,
**не полная верификация GPT/APFS, данных или частично выполненных патчей**.

До архивирования/очистки журналов успешная миграция сохраняет квитанцию.
Она привязана к SHA-256 prepared.plist; новые подготовки получают PreparationID.
Повтор полного восстановления сначала инвалидирует доказательства успеха,
затем очищает диски. Повреждённая квитанция не заменяется старыми логами.
Сведения о доступности patch-only входят в экспорт диагностики, без дисков,
тикетов, ROM и ключей.

**На телефоне: установить APK поверх 0.2.5, открыть мастер и нажать
«Завершить патчи» → «Запустить патчи». Не нажимать «Повторить восстановление»:
эта кнопка по-прежнему очищает рабочие диски и начинает запись сначала.**
В текущем архиве пользователя необходимые строки успешного restored найдены;
сами файлы дисков проверит приложение на телефоне.

## Проверки на Linux

- 64 JVM-теста: прежние 55 и девять новых checkpoint/patch-boot регрессий.
  Проверены сохранение содержимого/размеров девяти разреженных дисков,
  отказ без доказательств, миграция старого успеха и запрет старого успеха после
  нового RESET, повреждённая/чужая квитанция, полное обнуление только при
  полном restore, выбор двух ramdisk, HFSX compressed record и panic evidence.
- На ранее имевшемся stock ramdisk 18A5351d выполнен **реальный rewrite HFSX**
  производственным Kotlin-кодом, без загрузки гостя. У нужного job исходный
  data fork пуст, UF_COMPRESSED=32; новый XML имеет 418 байт, flag очищен.
  Его байты прочитаны обратно и совпали с ожидаемыми. Исходный ramdisk не
  изменился; длина IM4P сохранилась — 104685595 байт. Наличие реального
  `/usr/local/bin/restored_external` также проверено по каталогу HFSX.
- Хеши пяти прежних синтетических результатов остались равны ранее полученным
  результатам Swift (AP/SEP tickets, IMG4, job, injected ramdisk).
- APK/подпись/zipalign/native .so и итог lint фиксируются в validation-results.json.

Воспроизведение rewrite на собственном ramdisk после сборки Kotlin:

```sh
JAVA_HOME=/path/to/jdk GRADLE_USER_HOME=/path/to/gradle-cache \
  tools/patch-ramdisk-probe/run.sh /path/to/stock.im4p /path/to/output.im4p
```

Apple ramdisk/output и частные диагностические журналы в поставку не включены;
приложены probe source и JSON результата. **Успешный rewrite не доказывает
загрузку patch-only ramdisk.** Android launchd/монтирование/работа патчера,
частично изменённый кэш, потребление RAM и первый запуск iOS ещё не проверены.
При ошибке сохраняется неактивный набор и квитанция; повтор патчей возможен
без erase, но идемпотентность всех операций внешнего FS patcher не гарантируется.
