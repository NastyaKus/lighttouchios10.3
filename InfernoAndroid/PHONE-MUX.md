# 0.2.4: остановка `Mux magic`

## Что подтверждено диагностикой 0.2.3

На Android API 36 процесс проходит USB RESET, запросы дескрипторов,
SET_CONFIGURATION и VERSION/setup: последняя запись — `USB: usbmux v2 готов`.
Затем подключение к restored (62078) получает `IllegalArgumentException:
Mux magic` в GuestUsb.readMux. Сервис сохраняет исключение, останавливает
движок с кодом 0 и контролируемо завершает процесс VM. Это иной путь,
чем прежний SIGILL в переключении корутин: в этой попытке тот сбой не повторился.

Старый журнал не содержит байты проблемного v2-заголовка: бюджет USB trace
израсходован на NAK во время загрузки. Поэтому конкретное значение поля
по смещению 8 и состояние границ этого пакета **не установлены**. Извлечения
из частного журнала и сам архив диагностики в поставку не включаются.

## Сверка с источниками

- [GuestUSB.swift, исходный commit 4bc3970](https://github.com/MakrSas/Inferno-iOS/blob/4bc39702871f5a118d96acbad4df7a675ddf14e0/app/Sources/GuestUSB.swift):
  sendMux записывает host magic 0xfeedface; takeMux не проверяет это поле
  у устройства, а номер по смещению 12 возвращает в следующем host header.
- [usbmuxd device.c](https://github.com/libimobiledevice/usbmuxd/blob/master/src/device.c):
  send_packet записывает magic; device_data_input проверяет длину, но
  не требует равенства входящего magic. Не делает и проверки непрерывности
  mux-счётчика. Имена/выбор sequence-полей в этом клиенте отличаются от Swift;
  Android-порт сохраняет выбор offset 12 из своего исходного Swift-клиента.

Проверка magic и отклонение повторных/непоследовательных mux-номеров были
добавлены Android-портом. Fake USB до исправления тоже генерировал только
0xfeedface и возрастающие номера, поэтому не выявлял эту несовместимость.

## Изменения

- Приём v2 следует Swift: поле offset 8 не проверяется на host magic;
  offset 12 запоминается для echo. Mux-счётчик не используется для удаления
  TCP-пакетов. Проверки TCP byte sequence/окна и идентичности USB transfer
  остаются в силе.
- Сборщик принимает mux-кадр из нескольких USB transfer. Ограничение одного
  transfer остаётся 16384 байта; предел mux-кадра и входного буфера — 4 МиБ.
  Невозможные длины отвергаются до ожидания payload или выделения его размера.
- Первые 16 заголовков логируются отдельно от загрузочных NAK: protocol,
  length, reserved word, оба 16-битных поля. Payload, тикеты и ключи не пишутся.
- Изменены Kotlin-код и versionCode; engine и JNI не пересобирались.

## Воспроизводимые проверки

```sh
./gradlew :app:testDebugUnitTest :app:assembleDebug :app:lintDebug
```

ProtocolTest проверяет четыре разных reserved word (включая 0 и host magic),
эхо offset 12 при отличающемся offset 14, повтор/пропуск/переполнение mux-номеров,
TCP duplicate и TCP gap, границы фрагментов по 1/7 байт, совместный USB transfer
для VERSION и следующего v2 control, несколько coalesced кадров, mux payload
больше одного USB MTU, невозможные длины и ограниченный trace.
Это синтетическая независимая модель байтового устройства: она не исполняет
гостевой restored и не подтверждает реальное восстановление iOS.

## Следующий запуск на телефоне

Установить APK поверх прежнего Ember VM, сохранив данные. В мастере выбрать
повтор восстановления из уже подготовленного набора и подтвердить очистку
его целевого диска. IPSW/SEP key заново для этого не нужны. Не нажимать
«Подготовить набор», не удалять приложение и не очищать его хранилище.

Следующее доказательство — переход от mux к ответу restored, затем ASR,
успешный финальный статус и завершение патчера. При ошибке сохранить новую
диагностику. Полный restore и первый запуск iOS на 0.2.4 пока не проверены.
